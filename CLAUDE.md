## Commands

This project uses `npm` (`package-lock.json` is the only lockfile).

- `npm run dev` — start Vite dev server
- `npm run build` — type-check (`vue-tsc`) then production build
- `npm run test:unit` — run Vitest unit tests once and exit (`vitest run`, jsdom environment, rooted at `src/`)
- `npm run test:unit:watch` — same, in watch mode
- `npm run test:unit -- src/utils/__tests__/life.test.ts` — run a single unit test file
- `npm run test:e2e:dev` — run Cypress against the Vite dev server (interactive, opens Cypress UI)
- `npm run test:e2e` — run Cypress headless against the preview server (run `npm run build` first)
- `npm run lint` — `eslint . --fix` (flat config in `eslint.config.mjs`, includes Prettier)
- `npm run type-check` — `vue-tsc --noEmit` only

## Architecture

This is a small single-page Vue 3 + Vuetify + TypeScript app implementing Conway's Game of Life. There is no store (Pinia was removed as unused) — all state lives in component-local `ref`s.

- `src/main.ts` — app entry; registers Vuetify with a bare `createVuetify()`. Components and directives are imported on demand by `vite-plugin-vuetify` (`autoImport: true` in `vite.config.ts`), so only those used in templates are bundled. Only `vuetify/styles/core` is imported (not `vuetify/styles`, whose ~240kB of utility classes and ~40kB of material color classes were almost all unused), followed by `src/styles/utilities.css`, which copies into the same cascade layers just the utility/color classes in use (those in the templates, `bg-red` for the Stop button's `color="red"`, `elevation-1` that the slider thumb adds itself) and the `@property --v-elevation-overlay` registration the components rely on; add a class there when a template starts using one (an unlisted Vuetify utility class silently does nothing). Both are imported before `App.vue` so the components' own CSS comes after the base styles (the other order changes e.g. button font sizes).
- `src/App.vue` — root component; just composes `LifeGame`, `AboutGame` and `Note`.
- `src/utils/life.ts` — pure Game of Life rules: `countNeighbors(grid, i, j)`, `nextGeneration(grid)` (returns a new grid, does not mutate the input) and `isSameGrid(a, b)` (same size and cells). Cells outside the grid count as dead (no wraparound).
- `src/utils/line.ts` — `cellsOnLine(from, to)`: the cells on a straight line between two cells (both included, 8-connected, Bresenham), used to fill gaps in drag painting.
- `src/components/LifeGame.vue` — the game UI and state: holds the grid state (`dataMap`, a `number[][]` of 0/1), grid resize logic (`changeDataMapSize`, which resets `generation` to 0 when the size actually changes, like Random/Clear), drag painting (`startPaint`/`continuePaint` on `.map`, ended by `pointerup`/`pointercancel` listeners on `window`: `pointerdown` on a cell flips it and that new value is painted on every cell the pointer passes over; since browsers coalesce `pointermove`, `continuePaint` paints every cell on the line from the last painted cell (`lastPaintedCell`, reset on `pointerdown`/`pointerup`) to the new one via `cellsOnLine`, so fast drags leave no gaps; the cell is found with `document.elementFromPoint` (falling back to `event.target`) via the cells' `data-i`/`data-j`, since touch pointers stay captured by their first target; cells are `<button>`s with `aria-pressed` (alive) and `aria-label` (`Row i, column j`, 1-based); keyboard: the board is one tab stop via a roving tabindex (`focusCell`, clamped into the board as `focusedCell`), `moveFocus` on `.map` moves focus with the arrow keys/Home/End (Ctrl+Home/End for the corners), and Enter/Space toggle through the button's own `click`, which `toggleByKeyboard` handles only when `event.detail === 0` (a pointer click already toggled the cell on `pointerdown`); `.map` has `touch-action: none`, and `.box:hover` is inside `@media (hover: hover)` so it doesn't stick after a tap), the generation step (`step`, which applies `nextGeneration` once and returns `false` without changing anything if the board would not change), the simulation loop (`update`, which calls `step`), the Step button (`stepOnce`: `stopStatus()` then `step()`), and simulation start/stop (`changeStartStatus`/`stopStatus`). The simulation loop is a self-rescheduling `setTimeout` inside `update()` (not `setInterval`), gated by the `isStarted` ref. `update()` stops the simulation (`stopStatus()`) when `step()` returns `false`, i.e. the next generation equals the current one (all dead or only still lifes); oscillators such as the blinker keep running. Whenever `step()` returns `false` (auto-stop, or Start/Step on such a board) it sets `isUnchanging`, which shows "The board is no longer changing." in a `role="status"` line under the Generation counter; editing the board (pressing or dragging over cells, resize, Random, Clear) or a successful step hides it. The timer handle is held in a module-scoped `timerId` and explicitly `clearTimeout`'d in `changeStartStatus`/`stopStatus` before any (re)start, to avoid duplicate concurrent loops from rapid stop/start toggling. A `watch` on `interval` (the Generation Interval slider) does the same while running: it clears the pending timer and reschedules `update` with the new interval, so a change applies to the very next generation. The slider's visible label (`#interval-slider-label`) is tied to the thumb (`role="slider"`) with `aria-labelledby`, plus `aria-valuetext` in seconds (Vuetify passes `aria-*` attrs to the thumb, but `id` to the wrapper). The Start/Stop button text is `startButtonMessage` (`Start`/`Stop`, capitalized like the other buttons, since Vuetify 4's `v-btn` doesn't uppercase).
- `index.html` — page metadata: title/description, canonical, Open Graph and Twitter card (`summary_large_image` with `public/og-image.png`, 1200×630), JSON-LD, and the GA4 gtag.js snippet (`G-Z2N4Q3MS7Y`, shared with nulltemp.com), which loads the tag only when `location.hostname` is `life-game-vue.nulltemp.com`, so the dev server, `npm run preview`/Cypress and Cloudflare preview URLs aren't tracked. `sitemap.xml` is not in `public/`: the `sitemap` plugin in `vite.config.ts` writes it into `dist/` at build time with `<lastmod>` set to the last commit's date (the build date without git).
- `src/components/AboutGame.vue` — static card explaining the Game of Life rules and how to play (keep its "How to play" list, and README.md's "How to Play" and "Features", in sync when changing the UI).
- `src/components/Note.vue` — static footer card: GitHub and Ko-fi link buttons, and a Privacy Policy link.
- `@` path alias resolves to `src/` (configured in `vite.config.ts`).

### Grid semantics

- `dataMap` is row-major: `dataMap[i][j]` where `i` is row (height), `j` is column (width).
- Cells are `0` (dead) or `1` (alive), not booleans.
- Resizing (`changeDataMapSize`) mutates `dataMap` in place via `.length` truncation/extension rather than replacing the array — new cells default to `0`. Height/width are clamped to `[1, 100]` via `clampSize` before use, to guard against `RangeError` on negative sizes and runaway grids on very large ones. Blank or invalid input keeps the current size instead of clamping to the minimum, so it can't discard cells.
- Grid CSS columns are an inline `:style` binding driven by the `columns` computed (`dataMap[0].length`), not the `width` ref, so the layout doesn't reflow while the Width input is still being typed (before `change` resizes `dataMap`). Cells are square via `aspect-ratio: 1`, and the board's `maxWidth` (`mapMaxWidth`) shrinks for tall grids so the whole board fits in 500×500px. When either side exceeds `DENSE_SIZE` (40) cells, `.map` gets the `no-border` class and the cells' 1px borders are dropped. Cell colors come from Vuetify's theme CSS variables (live `rgb(var(--v-theme-primary))`, dead `rgb(var(--v-theme-surface))`, borders `rgba(var(--v-border-color), var(--v-border-opacity))`), so the board follows the light/dark theme (Vuetify 4's default theme is `system`). Cells have no color transition, since the update interval can be shorter than any transition.

### Testing structure

- Unit tests (Vitest) exercise the real code:
  - `src/utils/__tests__/life.test.ts` tests the rules in `src/utils/life.ts` with known patterns (block, blinker, glider).
  - `src/utils/__tests__/line.test.ts` tests `cellsOnLine`.
  - `src/components/__tests__/LifeGame.test.ts` mounts `LifeGame.vue` with Vuetify (a bare `createVuetify()`; the auto-import plugin in `vite.config.ts` also applies under Vitest) via `@vue/test-utils` and uses fake timers (only `setTimeout`/`clearTimeout`, so Vuetify/jsdom's internal `setImmediate` calls don't inflate `vi.getTimerCount()`) to drive the simulation loop. It stubs `ResizeObserver` (missing in jsdom), and `vite.config.ts` sets `test.server.deps.inline: ['vuetify']` so Vuetify's `.css` imports load under Vitest.
  - The Vitest root (`src`) and environment (`jsdom`) are set in the `test` block of `vite.config.ts`, not as CLI flags: with `--root src/`, Vitest 5 looks for the config file under `src/` and the `@` alias is lost.
  - `src/components/__tests__/App.test.ts` mounts `App.vue` and checks that `LifeGame`, `AboutGame` and `Note` are rendered.
  - Put new grid/rule logic in `src/utils/life.ts` and test it there; keep component tests for UI wiring.
- E2E tests (`cypress/e2e/*.cy.ts`) drive the real UI: grid cell count is asserted via `.box` element count, cell state via `.death`/`.live` classes, and the Height/Width inputs via `cy.contains('.v-text-field', '<label>').find('input')` (Vuetify does not put the label on the `<input>`). Grid resize fires on the input's `change` event, so tests `.blur()` after typing. Drag painting is tested by `trigger`ing `PointerEvent`s (`eventConstructor: 'PointerEvent'`) on the cells themselves, so each event gets that cell's center as `clientX`/`clientY` and the app resolves it through `document.elementFromPoint` (the path jsdom can't cover); the Step button and the "no longer changing" message are covered too.
- `test:e2e` / `test:e2e:dev` bind the server to `127.0.0.1:4173` explicitly (matching `baseUrl` in `cypress.config.ts`); on Windows `localhost` may resolve to `::1` and `start-server-and-test` would time out. If Cypress fails with `bad option: --smoke-test`, the shell has `ELECTRON_RUN_AS_NODE` set (e.g. inherited from VS Code) — unset it.

## Deployment and CI

- The app is hosted on Cloudflare (https://life-game-vue.nulltemp.com/); the production build is `npm run build` → `dist/`.
- Response headers are set in `public/_headers` (copied as-is into `dist/`): `nosniff`, `Referrer-Policy`, `X-Frame-Options: DENY` on every path, and a one-year immutable `Cache-Control` for the hashed `/assets/*`. There is no CSP yet (it would need to allow the GA hosts).
- CI is GitHub Actions (`.github/workflows/ci.yml`), run on pushes to `master` and on pull requests: `npm ci` (with `CYPRESS_INSTALL_BINARY=0`), `npx eslint .` (no `--fix`), `npm run type-check`, `npm run test:unit`, `npm run build-only`, on Node 22, in the `check` job. A separate `e2e` job runs the Cypress specs headless via `cypress-io/github-action` (which installs dependencies with the Cypress binary, runs `npm run build-only`, then `npm run test:e2e` as its `command`, so `start-server-and-test` serves `dist/` on `127.0.0.1:4173` and runs `cypress run`; the action's own `start`/`wait-on` is not used, since its ping fails on the first `Socket closed before the connection was established` instead of retrying), uploading `cypress/screenshots` as an artifact on failure. Still run `npm run test:e2e` locally when changing UI.
- `package.json` `overrides` force `js-beautify` (via `@vue/test-utils`) onto `glob` 14 and `editorconfig` 4, whose `minimatch` 11 fixes the `npm audit` advisories in `glob` 13 / `minimatch` 10 (`js-beautify` 2.0.3 still asks for `glob ^13` / `editorconfig ^3`). Drop them once `js-beautify` depends on fixed versions itself.
